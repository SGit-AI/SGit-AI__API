# DevOps Research — Can a Claude agent deploy, smoke-test and destroy the vault API through cloud MCP servers?

**version** v0.1.6 · **date** 2 October 2026 · **role** DevOps (Villager) · **asked by** Dinis (voice, 2 Oct)
**question** If a Claude agent in a dev environment is given the Cloudflare MCP (under an agent behaviour policy), how hard is it to deploy the new vaults.sgit.ai API with it — and do AWS, Azure and GCP have equivalents — so the agent can set up, test, tear down, and CI then repeats it?
**method** Web survey of vendor docs (2 Oct 2026) plus probes from this cloud sandbox. Anything not verified against a vendor doc is marked *unverified*. Vendor pages were read through a summariser, so quotes are as relayed.

---

## 1. Answer in one table

| Cloud | Official MCP for deploying | Transport / auth | Runs our image (~250 MB Python + uvicorn) with a public HTTPS URL? | Teardown through the MCP | Difficulty for "agent deploys, CI repeats" |
|---|---|---|---|---|---|
| **Cloudflare** | Cloudflare API MCP (`mcp.cloudflare.com/mcp`, 2,500+ endpoints via `search`/`execute`) + Workers Bindings / Builds / Observability servers; all remote, OAuth, GA | Remote Streamable HTTP; OAuth or scoped API token | **Only via Cloudflare Containers** (GA 13 Apr 2026). Workers alone: **no** — Python Workers are Pyodide in a V8 isolate, no uvicorn, no ASGI. And the container needs a small JS Worker as its HTTP front door | Partial: API deletes via `execute`; image lifecycle is `wrangler` only | **Medium** — the MCP cannot build or push the image or run `wrangler deploy`; the agent still needs Docker + wrangler + a token |
| **AWS** | **AWS MCP Server** (managed, GA 6 May 2026; one `call_aws` tool over 15k+ APIs, CloudTrail-logged) + awslabs local servers: **ECS MCP** (`containerize_app`, `build_and_push_image_to_ecr`, `delete_app`), Serverless (SAM), IaC (CFN/CDK) | Managed: IAM identity (the OAuth-to-SigV4 bridge is *unverified* from AWS docs). Local: stdio + `AWS_PROFILE`/env creds | **Yes** — ECS Express Mode / App Runner / Lambda container image; our `lambda.cfn.yml` already deploys the image | **Yes** — `delete_app`, `cloudformation delete-stack` | **Medium** — managed-server auth in a sandbox is under-documented; local ECS server needs Docker + creds; `ALLOW_WRITE` is off by default (good) |
| **Azure** | **Azure MCP Server 2.0** (GA; `npx @azure/mcp`, Docker image, self-hostable remote) | Local stdio; Entra ID via `DefaultAzureCredential` (SP secret, `az login`, managed identity) | **Yes** (Container Apps) — but there is **no Container Apps or ACR-push namespace** in the tool list (`acr` is list-only, `group` is list-only); deploys go through the `deploy` tool, `azd`, or the `az` passthrough | **Yes** — `az group delete` wipes a resource group (cleanest of the four), but via passthrough, not a first-class tool | **Medium/Hard** — the agent needs `az`/`azd` + Docker + a service principal; the MCP is thin for deploys |
| **GCP** | **Google-managed remote MCP servers** (50+, announced 28 Apr 2026; auto-enabled with the API) incl. **Cloud Run MCP** `run.googleapis.com/mcp` (**GA**: deploy from image, list, logs) + local `cloud-run-mcp` | Remote OAuth 2.0 + IAM; scopes `run` / `run.readonly`; needs `roles/mcp.toolUser` + Cloud Run roles | **Yes** — Cloud Run from an image in Artifact Registry | Delete via MCP *unverified*; `gcloud run services delete` / project delete reliable | **Easy/Medium** — the only one where deploy-from-image is a first-class remote MCP tool with no secret in the agent; image must already be pushed |

**Plain statements the marketing blurs:**
- Cloudflare says "FastAPI … easy to install" on Python Workers. That is FastAPI *routing* inside Pyodide, not a uvicorn process; our image cannot run on Workers. Containers is the only Cloudflare path, and it is a Durable-Object-fronted container, not a plain `docker run`.
- Cloudflare's "Container MCP" (`containers.mcp.cloudflare.com`) is a *sandbox dev environment* product, not a way to manage Containers deployments.
- Azure's overview says "build and deploy apps to Azure"; the first-class tools are mostly list/read, and the overview lists a GitHub Copilot subscription as a prerequisite (irrelevant for Claude Code; *unverified* whether it is enforced).
- AWS's "zero credential exposure" for the managed server still needs a credential source behind the local proxy.

| Probe | Result |
|---|---|
| Reach `api.cloudflare.com`, `sts.amazonaws.com`, `management.azure.com`, `run.googleapis.com` through the proxy | all reachable (301/302/400/404 = answered) |
| Reach `ghcr.io`, Docker Hub | reachable |
| Docker installed | **yes** (`/usr/bin/docker`) |
| `aws`, `az`, `gcloud`, `wrangler`, `terraform` installed | **none** — all installable in a session-start script (pip/npm/zip) |
| MCP connectors attached to this org | only Google Drive (not connected). Registry search needs **"connector suggestions" enabled in Claude settings** before an agent can see what is available |
| Claude Code remote MCP support | `claude mcp add --transport http <name> <url>` + OAuth; claude.ai connectors flow into cloud sessions when logged in with a claude.ai subscription (not with an API key) |

So the honest baseline today: **this agent could already deploy to all four clouds with CLIs and OIDC/short-lived credentials in a setup script, with no MCP at all.** The MCPs change *who holds the credential* and *what the agent can do without a shell*, not whether the deploy is possible.

## 3. Auth: where the secret lives, and the least-privilege pattern each vendor documents

| Vendor | Dev session (agent) | CI | Vendor-documented agent policy |
|---|---|---|---|
| Cloudflare | MCP: OAuth, no secret in env. `wrangler`: `CLOUDFLARE_API_TOKEN` in env | API token (scoped) | Scoped API tokens (Workers Scripts, R2, DNS edit on one zone); no agent-specific policy beyond that |
| AWS | Managed MCP: IAM identity via proxy (*unverified*). Local servers: `AWS_PROFILE` or env creds | GitHub OIDC → IAM role (our `github-oidc-role.cfn.yml` already does this) | IAM policies/SCPs; ECS MCP's `ALLOW_WRITE` / `ALLOW_SENSITIVE_DATA` flags off by default; CloudTrail logs every `call_aws` |
| Azure | SP `AZURE_CLIENT_SECRET` or `az login` | Workload identity federation (OIDC) | RBAC on one resource group; server flags `--read-only`, `--namespace`, `--mode`; elicitation before high-risk tools; docs warn about autonomous clients |
| GCP | OAuth, **no secret**; SA key avoidable | Workload Identity Federation | **Clearest of the four**: "create a separate identity for agents", `roles/mcp.toolUser` (`mcp.tools.call`) + minimal resource roles, `run.readonly` scope for smoke tests |

This maps directly onto the "agent behaviour policies" idea: GCP's `mcp.toolUser` + scoped OAuth is the shape you want; AWS gets there with an IAM role per agent and CloudTrail; Cloudflare with a scoped token per agent; Azure with a custom RBAC role per resource group.

## 4. What it would take, per cloud, for the vaults API specifically

The artefact is one image (phase 1, D4). Everything below assumes it is published to a registry on tag (`ghcr.io/sgit-ai/vaults`, Q4).

| Cloud | Agent path (dev session) | CI path | Teardown | Fits the README test? |
|---|---|---|---|---|
| **GCP Cloud Run** | Cloud Run MCP (OAuth) → deploy from image → public URL → smoke → delete via `gcloud` (or MCP, *unverified*) | `gcloud run deploy --image …` with WIF | `gcloud run services delete`; or one project per experiment and `projects delete` | Yes — one command, already in the deploy vault's Cloud Run page |
| **AWS** | Managed AWS MCP `call_aws` for CFN deploy of `lambda.cfn.yml` (image Lambda + Function URL) or ECS MCP Express Mode; smoke; `delete-stack` / `delete_app` | `deploy-full-cycle.yml` with OIDC (exists, never run live) | CFN stack delete; ECR force-delete | Yes — the CFN templates exist; this is the first live run we have been waiting for |
| **Cloudflare** | API MCP for DNS/R2 only; deploy needs `wrangler containers push` + a wrapper Worker (JS) + `wrangler deploy` in the shell | `wrangler deploy` with token | `wrangler delete` + API deletes | Only if we write and maintain a Worker front door — **net-new work**, and it changes the topology (DO-fronted container) |
| **Azure** | Azure MCP `deploy` / `az` passthrough: `az containerapp up --image …`; smoke; `az group delete` | `az containerapp up` / Bicep with OIDC | `az group delete` (one call, everything) | Yes, but via CLI inside the MCP; the MCP adds little over a shell |

## 5. Recommendation

1. **Order of attack:** GCP Cloud Run first (best MCP, no secret, matches the one-image model), AWS second (our templates, our existing OIDC design, the managed MCP with CloudTrail), Azure third (works, MCP is thin), Cloudflare last and only for DNS/R2 — unless you specifically want the Workers edge, in which case Containers is a separate small project (a wrapper Worker) and should be scoped as one.
2. **Grant the MCPs, but design for the CLI.** Every one of the four reproduces in CI without the MCP. The MCP's value is interactive: the agent deploying from a dev session with a credential it never sees. So: an agent identity per cloud (GCP `mcp.toolUser`, AWS IAM role, Azure RBAC role, Cloudflare scoped token), attached as a connector, and the *same* operations scripted in `deploy/` for CI. The README test then has one answer for humans, agents and pipelines.
3. **Two things to enable now, no cost:** turn on "connector suggestions" in Claude settings so agents can see the org's connectors; add the four CLIs to the session-start script of the vaults repo (the `session-start-hook` skill does exactly this).
4. **One thing to resist:** granting a long-lived secret (`AWS_ACCESS_KEY_ID`, `AZURE_CLIENT_SECRET`, `CLOUDFLARE_API_TOKEN`) to a dev-session agent "to make it work". GCP and Cloudflare are OAuth-native; AWS and Azure both have OIDC paths. Phase 2's secrets vault is the right home for whatever cannot be short-lived.
5. **Pre-flight before any of this:** steps 1.2–1.5 of the phase-1 pack must land first — there is no image to deploy yet. The first live AWS run is already gated on the OIDC bootstrap (Q3).
