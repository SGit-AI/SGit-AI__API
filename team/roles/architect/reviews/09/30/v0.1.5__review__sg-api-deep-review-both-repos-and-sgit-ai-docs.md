Two observations that matter for the split:

- **The sgit protocol proper is small**: vault pointer + presigned + info = 22 paths. The CLI
  also probes `/api/auth/whoami`, which does not exist on this API (the doctor degrades
  gracefully). Transfers/early-access/public-preview (19 paths) are SG/Send tenants; the vault
  UI depends on transfers, so they are not dead code — they just are not "sgit".
- **Auth is inconsistent across route classes.** `Routes__Vault__Pointer` and
  `Routes__Vault__Append` go through `Service__Access_Token` (TTL-cached Admin lookup, env-var
  fallback). `Routes__Transfers`, `Routes__Presigned`, `Routes__Vault__Presigned` each carry a
  verbatim uncached copy of the same logic; `Routes__Transfers` additionally accepts the
  token as a query parameter. Behaviour is equivalent; only the cache differs. This is a
  post-move cleanup, not a move-time change.

## 3. What the dev pack got right, and what it missed

The pack (00–05) is sound and the pre-move review of 17 Aug closed its open caveats
(`/join/*` really is orphaned; `Deploy__Service` UI bundling now conditional; the hidden
test-order dependency fixed). Its "move with zero changes, then delete" discipline should stand.

Gaps found in this review that the pack and the pre-move review do not cover:

1. **ADR-1's "zero coupling" is import-level only.** At runtime the User Lambda calls the Admin
   Lambda for token validation when `SGRAPH_SEND__ADMIN__BASE_URL` is set. The extracted repo
   therefore has *two* auth modes to document: hosted (Admin Lambda lookup) and self-hosted
   (`SGRAPH_SEND__ACCESS_TOKEN` env-var single-key mode, which is what every deploy.sgit.ai
   page already assumes). The env-var mode already exists in `Service__Access_Token.check()`,
   so no code change is needed — but the README test cannot pass without saying so.
2. **The deploy artefact and the deploy docs point at different things** (summary item 3).
   The pack's identical-output test is the Lambda **zip**; deploy.sgit.ai's seven targets are
   all the **container image**. `deploy/aws/lambda.cfn.yml` itself is a *container-image*
   Lambda, not the zip Lambda the pytest deployer creates. So today the origin repo has two
   Lambda deployment shapes, and only the one nobody documents is moving.
3. **Two-track dependency pinning survives the move and needs an owner.** Lambda runtime deps
   are hard-pinned in `APP__SEND__USER__LAMBDA_DEPENDENCIES` (`user__config.py`) and packed by
   `Lambda__Dependencies__Builder` for **Python 3.13 / x86_64** (`LAMBDA_PYTHON = '3.13'`,
   `manylinux2014_x86_64`; the deploy test also forces `Runtime='python3.13'`). `pyproject.toml`
   uses wildcards; the container is `python:3.12-slim`. Both `CLAUDE.md` files say
   "Python 3.12 / arm64". Pick one truth per target and write it down.
4. **`mgraph-ai-service-cache` + `-client` come along for one constant.** They are in the
   Lambda pins, in `DEPENDENCIES__TRACKED`, and imported once in `Deploy__Service.py` for
   `ENV_VAR__CACHE__SERVICE__BUCKET_NAME`. Not to be removed during the move (rule), but it is
   the first thing to record in `05__deletion-candidates.md` for the new repo.
5. **The package name is part of the wire contract.** `Routes__Info__SGraph.versions()` returns
   a dict keyed `sgraph_ai_app_send`, and `test_smoke__deployed_target.py::test_2` asserts that
   string. A rename to `sgit_ai_api` changes a response body — which is precisely the ADR-7
   "rename, not move" major bump, and must be called out in the release note.
6. **`Send__Config` auto-selects S3 when AWS credentials are present.** In the new repo's CI,
   any job that assumes an OIDC role before running tests will silently flip the suite to S3
   mode (this bit the pre-move session in the cloud sandbox: ~32 failures). The test job must
   set `SEND__STORAGE_MODE=memory` explicitly.
7. **Long-lived AWS keys vs OIDC.** The origin's Lambda deploy jobs use four long-lived secrets;
   the full-cycle workflow uses OIDC only. The new repo should start OIDC-only (the deploy
   docs vault's `runbooks/new-aws-account` already describes exactly that role).
8. **Deletion candidate 3** (`APP_SEND__UI__USER__*` constants) will move unless trimmed; the
   pack says do not trim during the move. Move it, record it, trim in the deletion series.

### 4.2 Naming and scope (ADR-2) — unrecorded decision

### 4.3 The deploy.sgit.ai mismatch — the structural finding

This repo's vault says, page after page, "`docker run diniscruz/sg-send-vault`",
"`ImageUri=…/sg-send-vault:latest`", "the image is Cloud Run-ready". Its `scripts/README.md`
says plainly: "the deployment scripts live in the SGraph-AI__App__Send repo under `deploy/`
— this vault documents them; the repo is their source of truth." That was accurate for the
SG/Send team's vault. It is not a tenable end state for a repo whose README test is "deploy
the API from here".

The container's coupling to the origin repo is real but shallow:

- `sgraph_ai_app_send__docker/` — 8 files: container app (subclass of the User app), login
  route, TLS launcher + schema, `serve.py`, `app.py`, Dockerfile, README.
- The Dockerfile's only origin-only step is `scripts/build-vault-static.sh` overlaying four
  UI trees into `/app/static_vault`. Everything else is `pip install -e .` + uvicorn.

An **API-only image** (no UI overlay; root serves the login page or a JSON pointer) is buildable
from the new repo the day the package lands, and is what Lambda-container, Fargate, Cloud Run
and Heroku need from an *API* repo. The joint API+UI image then becomes what the pack already
says it is — a later piece of work — but built *on top of* the published `sgit_ai_api` package
rather than a sibling copy. This is PROPOSED and is a scope addition to the pack; it needs
Dinis's yes (§6).
