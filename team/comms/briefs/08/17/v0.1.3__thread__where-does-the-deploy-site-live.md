## The question

[sgit.ai/deploy](https://sgit.ai/deploy/index.html) renders self-hosting guidance live
from an encrypted vault (the mechanism is documented in the
[live-vault-docs case study](https://sgit.ai/case-studies/live-vault-docs.html)): the
SG/Send team writes markdown, `sgit push`es it, and the next page load has it — sgit.ai
stores only a read key and an endpoint in `deploy/vault.json`, plus a freshness window
(`ref_ttl_s: 120`). The objective is that everything those pages describe deploys **from
this repository**. So: where should the deploy docs vault — and its config and help —
live once the API does?

## The property that must survive any answer

**Publishing deploy docs must stay a vault push.** No sgit.ai deploy, no build step, no
content sync. Whoever hosts the vault, `sgit push` remains the entire release process,
and sgit.ai (or any other front-end) holds only a read key. That is the demonstrated
value of the current setup and it must not be traded away for tidiness.

## Options

### A — This repo owns the deploy docs vault (recommended)

The deploy docs describe deploying the code in this repo; the README test ("deploy from
this repository, following only its README, asking nobody") means the docs and the code
must move in lockstep — same commits, same reviews, same CI. This repo already has the
side-by-side pattern working (the reference vault): working tree in git, ciphertext
mirror committed, credential tier ignored and leak-guarded by a unit test.

Shape: a **second vault** (`deploy-docs`, distinct from the conformance reference vault
— see the tension below), living at `deploy_docs/` in this repo. Published two ways:
1. `sgit push` to the live SG/Send server — so sgit.ai/deploy keeps working exactly as
   today, with only the read key/vault id in its `deploy/vault.json` updated once.
2. Projected to this repo's GitHub Pages alongside the reference vault — a second,
   serverless read origin for the same content, and this repo's own docs page.

Ownership: the API team writes the deploy docs (they own the deployment code); the
write key is escrowed with Dinis; pushes to the live server can be automated as a CI job
(token in GitHub Actions Secrets) or stay a human act — sub-thread 3.

### B — Stays with the SG/Send team's vault until the extraction lands

Least churn now, and the current owners keep their workflow. Cost: from the moment
deployment code starts landing here, the docs describe a repo they do not live in —
drift is structural, and the README test is being graded on someone else's homework.
Acceptable as a transition state; wrong as an end state.

### C — Fold deploy docs into this repo's existing docs vault (`ivpijuvg`)

One vault, fewer moving parts. Rejected as the recommendation because the reference
vault has a second job: it is the **conformance target**, deliberately small, stable and
representative — CI serves it, tests pin it, and its churn should approximate zero.
Living deploy docs churn constantly. Two vaults, two jobs.

### D — Static-only: the deploy vault served from GitHub Pages, no live server at all

The in-browser reader is ~90 lines (this repo now ships one — `pages/reader.js`) and
sgit.ai/deploy could read the vault from a Pages origin instead of the SG/Send API.
That would make the deploy docs themselves zero-backend. Two things to verify before
this is more than a note: GitHub Pages' cross-origin defaults for the sgit.ai origin
(no custom headers are configurable there), and whether the 120s freshness window
behaves acceptably behind the Pages CDN cache. Also a real trade: the live-server path
is itself part of what sgit.ai/deploy demonstrates. Keep as a follow-on experiment, not
the first move.

## Recommendation

**A**, with **B as the explicit transition**: the vault stays where it is until the
extraction's first deploy job is green in this repo, then the deploy docs move here (or
are re-created here — republish, don't retrofit, per the publishing method), sgit.ai's
`deploy/vault.json` is updated once, and the SG/Send team hands the write key to escrow.
**D** is run later as an experiment on top of A (the content is then already here and
already projected to Pages — it costs one config change to try).

## Sub-threads to resolve

1. **One vault or two on this repo's Pages origin?** Recommendation above says two
   (reference/conformance vs deploy-docs). Anyone want to argue for one?
2. **Same vault id as today's `fyofmkvr`, or a fresh vault?** Fresh vault + republish
   keeps history clean and follows the republish-don't-retrofit rule; same vault keeps
   sgit.ai's config untouched. Leaning fresh.
3. **Who pushes to the live server, and from where?** A human with the escrowed key, or
   a CI job on merge to `dev` with a scoped token in Actions Secrets? CI push is
   consistent with "docs move with code", but puts a write token in CI — the first one
   this repo would hold. Needs an explicit decision.
4. **Config location:** `deploy/vault.json` stays on sgit.ai (their page, their TTL
   knob). This repo should publish the *canonical* read key + endpoint in one place
   (proposed: the vault's own README and this repo's Pages `llms.txt`) so sgit.ai's
   config is derivative, not authoritative.
5. **Help/support surface:** where do "it didn't work" reports go — repo issues here,
   or sgit.ai? Proposed: issues here (the code is here), linked from the deploy pages.

## Constraints carried in from the corpus

- A published read key is permanent; escrow the write key before publishing (14 Aug).
- "Publish = push": a vault that was only init+committed serves an empty named branch —
  the publish pipeline must include the push, wherever it runs (verified here, 17 Aug).
- Pages/static hosts cap size and offer no rate limiting — the deploy vault is a
  projection of head, never a mirror with history (v0.33.59 brief).
