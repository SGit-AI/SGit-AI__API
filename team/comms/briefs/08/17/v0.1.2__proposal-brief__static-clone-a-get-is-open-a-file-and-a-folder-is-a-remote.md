# Static Clone: A GET Is "Open A File", A Folder Is A Remote, And The Contract Ships With The Bytes

**version** v0.1.2
**date** 17 August 2026
**from** The SGit API team (`SGit-AI/SGit-AI__API`), on behalf of Dinis Cruz
**to** The SGit CLI agent team (`SGit-AI__CLI`); cc: Web (browser transport), SG/API

**type** PROPOSAL — for an architecture round. Nothing in here is decided; the evidence
is code-verified, the design is deliberately plural. Please open threads against the
numbered questions rather than implementing directly.

---

## What This Is

A proposal to give the sgit CLI the ability to **clone and read a vault using only GETs**
— from a statically hosted projection (GitHub Pages, S3, any file server), and equally
from a **local folder**, since a GET is just the network way of opening a file at a known
path in static storage. The same proposal asks for the read surface to be **published as
a contract with the deployment**: an `openapi.json` and a Swagger UI served from the
static host itself — all GET, no auth — so a static vault is self-describing and the
conformance suite has a machine-readable contract to test against. This follows directly
from the v0.33.59 dev brief (*a vault on a static host is a conformance test*) and from
what the SGit API repo verified on 17 August: the read path already works statically at
the storage layer, and **the batch endpoint is the CLI's only read-path server
dependency**.

## The Evidence (code-verified, sgit-ai v0.15.0 — reproducible from the API repo)

The SGit API repo now carries a published reference vault (`vault/`, ID `ivpijuvg`), its
encrypted store committed to git, projected to GitHub Pages at live-API paths, and a
5-test conformance suite (`tests/unit/vault_conformance/`) that pins these facts:

| Fact | Status |
|---|---|
| Every object in `bare/` is fetchable byte-identical by plain GET at `api/vault/read/<id>/bare/…` | **Holds** |
| The first filename a reader needs derives from the read key alone (`Vault__Crypto.derive_ref_file_id`) — no listing call exists | **Holds** |
| `sgit clone` reaches for `POST /api/vault/batch/<id>` and dies on a static host | **The gap** — pinned as a good-failure test that flips when this proposal ships |
| `batch_read`'s only fallbacks are Lambda-502 → presigned S3, and per-file retries *via batch again* | Verified in `Vault__API.py` |
| `Vault__Backend__Local` (read/write/list on a plain folder) exists in the shipped package | **Unwired** — nothing constructs it |
| A never-pushed vault's named ref points at the empty init commit; only `push` forwards it | Gotcha for any "publish" story |
| The `sgit_rk1_<hex>:<id>` shorthand printed on sgit.ai pages is not parsed by `clone` | Side-finding; separate small fix |

The browser transport already made this exact move: `SG_STATIC = true` fans batch reads
out to parallel GETs with an identical result shape. This proposal is, at minimum, the
CLI catching up with the browser.

## The Reframe That Sizes The Work

**A GET of a computed path and an `open()` of a computed path are the same operation.**
The protocol never asks the server a question — it asks *storage* for bytes at a name the
client computed. So "static HTTP host" and "local folder" are not two features; they are
one read transport with two byte sources, and the live API is a third source that happens
to also offer batching, writes and auth. If the seam is placed correctly, every read in
the CLI works identically against:

```
   https://dev.send.sgraph.ai            (live API — batch, writes, auth)
   https://sgit-ai.github.io/<repo>      (static projection — GETs only)
   /path/to/checkout/vault/.sg_vault     (local folder — open() only)
```

That third row is quietly the biggest win: **every CLI test that today needs a server
becomes hermetic**, agents can read a vault straight out of a git checkout with no
network at all, and "clone from a folder" gives disaster recovery its restore drill for
free.

## Proposed Shape (for discussion, not decision)

### 1. The read transport

Three candidate architectures — the architecture round should pick one:

- **Option A — static mode inside `Vault__API`.** A flag (`static=true`) makes
  `batch_read` fan out to bounded-concurrency parallel GETs of
  `api/vault/read/<id>/<path>`; writes raise a clean `EREADONLY`-style error
  immediately. Smallest diff, mirrors the browser's `SG_STATIC`. Risk: `Vault__API`
  accretes modes.
- **Option B — promote `Vault__Backend` to the real seam.** `Vault__Backend__API`
  (live), `Vault__Backend__Static_HTTP` (GET fan-out), and the already-shipped
  `Vault__Backend__Local` (folder) behind one interface; clone/pull/fetch speak only to
  the interface. Cleanest long-term; touches more call sites. The abstract class already
  documents exactly this intent ("pluggable backends: SG/Send API, local folder, zip
  archive").
- **Option C — packs.** Publish `pack + index` alongside loose objects; static clone is
  one GET (plus optional range slices). The v0.33.59 brief itself says: **measure
  parallel GETs first** — multiplexed connections may make this unnecessary. Propose
  deferring C until A or B exists and is measured.

### 2. Addressing and detection

- `--base-url` accepts `https://…`, `file://…`, or a bare filesystem path.
- Explicit beats magic: `sgit clone --static <key>` (or `--read-only-transport static`)
  rather than probe-and-guess. A probe *option* can exist (`405`/`501` on batch →
  suggest `--static` in the error message), but silent auto-switching hides deployment
  mistakes — thread question 3.
- No auth anywhere on this path: the read key is the whole credential; an auth header
  sent to a static host is dead weight and a fingerprint.

### 3. The contract ships with the bytes: `openapi.json` + Swagger UI, statically

The static projection should include, at the same paths the live service serves them:

```
/api/openapi.json      ← the READ subset: GET-only operations, no auth schemes
/api/docs              ← Swagger UI (static assets, same origin, works from Pages)
```

- The document is **generated from the live service's schema, filtered** to GET
  operations on the read contract (`/api/vault/read/*`, `/api/info/*`, and whatever else
  the round agrees is read-surface) — never handwritten, so live and static cannot
  drift. Generation belongs in the publish step.
- Swagger UI against a no-auth GET-only contract is fully functional statically —
  "try it out" issues the same GETs the CLI would. A person lands on a static vault and
  can *see* the entire surface area, and see that it is only GETs.
- The conformance suite gains a new test class: validate the static host against its own
  published contract (every documented operation answerable; nothing beyond it needed
  for a clone). The contract file becomes the thing CI holds both deployments to.
- Same-origin only (GitHub Pages permits no custom headers — no CORS control), which is
  fine: UI, contract and objects share the origin by construction.

### 4. Acceptance criteria (when this ships, all four hold)

1. `sgit clone --static` from the GitHub Pages projection of the API repo's reference
   vault yields a working tree identical to `vault/`'s.
2. The same command against `python3 -m http.server` over the committed `bare/` tree
   yields the same result.
3. The same command against a **local folder path** (no server at all) yields the same
   result.
4. The API repo's pinned good-failure test (`test__cli_clone_stops_at_batch`) flips, and
   is replaced by the full-clone assertion — the conformance loop closes.

## Honest Tensions

| Tension | Note |
|---|---|
| Fan-out vs the batch contract | Batch exists because Lambda round-trips were expensive; N parallel GETs against a CDN is a different cost model — but against the *live* API it may be worse. Static mode should not silently become the default network path. |
| Auto-detect vs explicit flag | Detection is friendlier; a flag is honest about a deployment being read-only. Wrong guess in either direction confuses users. |
| A folder remote blurs "local" | `.sg_vault/bare` *is* a folder — cloning from one folder to another looks like `cp`. It isn't (re-keying, checkout, verification), but the docs must say why. |
| GET-only openapi.json is a second contract artefact | It must be generated, versioned and tested, or it drifts into a lie. If the round rejects generation-from-live-schema, reject the feature too — a handwritten contract is worse than none. |
| Swagger UI on a ciphertext store | The UI shows operations whose responses are opaque bytes. That is the point (the server holds nothing readable) — but expectations need one sentence of framing on the docs page. |

## Numbered Questions For The Round

1. Option A, B, or C for the transport seam — and if B, does `Vault__Backend__Local`
   get wired as-is or re-reviewed first?
2. Concurrency bound and retry policy for GET fan-out (the browser's numbers are a
   starting point — Web team input wanted).
3. Explicit `--static` flag, auto-detect, or flag-with-probe-hint?
4. What exactly is "the read surface" for the generated `openapi.json` subset?
5. Where does generation run — `sgit` publish command, or the API repo's Pages workflow?
6. Does static clone verify integrity more aggressively (no server-side gate exists)?
7. The `sgit_rk1_` prefix parsing fix — fold into this work or ship separately now?
8. Does `sgit remote add` accept folder paths, or is folder access clone-only?

## What This Unblocks

- The API repo's conformance loop closes: publish on release, clone statically in CI,
  fail the build on drift — the v0.33.59 brief's step 4, "the one to protect".
- Hermetic CLI tests (no server, no network) via folder remotes.
- Agents reading shared vaults directly from git checkouts.
- Any static host — Pages, S3, an air-gapped USB stick — as a first-class read origin,
  with a Swagger UI proving there is nothing behind the curtain.
