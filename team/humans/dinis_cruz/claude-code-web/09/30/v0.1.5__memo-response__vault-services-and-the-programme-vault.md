## 2. The next phase — what I heard, and what is true today

The memo names seven capabilities. Code-verified against both repos and the reality docs:

| Capability | Exists | As primitives only | Missing |
|---|---|---|---|
| Three auth modes (open / env key / delegated) | ✅ two and a half — `Service__Access_Token` has open, env key, and *delegated to a server* (Send's Admin Lambda) | | the **vault-backed** delegate |
| Existence check for a key | | `GET /api/vault/health/{id}` (vault-level), 404 on `read` (file-level), batch | a key *service*; note the append gate deliberately refuses to be an existence oracle (09/08) |
| PKI-signed requests | | `sgit keygen/sign/verify` (RSA-OAEP 4096 + ECDSA P-256, file-level); browser SecureChannel; an admin `/keys/*` prototype | signed-request verification on any route; a registry with revocation |
| Zip / backup | | `/api/vault/zip`, `sgit export` | the schedule, the restore drill; **vault-key rotation cannot exist** (the key is the identity; only migration) |
| API-key management | | the 08/06 design ("credential ≠ address", four vaults, append token on the hot path) | any code |
| Secrets / KV endpoints returning ciphertext | | browser-only owner-secrets under `.vault/owner/secrets/` | any server-side service; `sgit secrets` is PROPOSED |
| Observability of vault traffic | | | everything: analytics middleware disabled since 22 Feb, vault reads deliberately uninstrumented, LETS never built — and therefore **no data** for "only the features we actually use" |

**The shape I propose** (`01` in the phase-2 folder): a deployment holds **one keypair**; with it, it opens a few **supporting vaults** — credentials, secrets, config/kv, telemetry, backup — that are ordinary vaults living on the same deployment, another one, or a static host. Three thin **apps endpoints** (`/api/apps/keys`, `/kv`, `/secrets`) are PKI-gated projections that return ciphertext the caller decrypts: no server-side plaintext, no new storage, a shorter path to an existing read. **Auth mode 3** is that loop applied to the deployment's own tokens — "is this token valid?" becomes "is there a live record at `keys/<H(token)>` in my credentials vault?" — which is what finally cuts the Send Admin dependency and lets tens of deployments share one credentials vault with no shared server. Rotation is a weekly job that issues, publishes, revokes-after-grace, exports the supporting vaults to a backup vault, and **runs a restore drill**. Observability is the 09/07 design as written: one record per (channel, hour) into a telemetry lane, never per request. Deploy is `sgit deploy`, which creates the supporting vaults on first boot; the ephemeral deploy server is the same script behind a Router Lambda, and our own CI is its first customer.

**Two things to say plainly:**

- **This is Explorer work, every line of it.** It goes on a branch of the new repo from step 1.2 and mounts *beside* the phase-1 app; it never touches phase 1's contract, or the parity proof dies. Sequencing is P2-D1.
- **Pruning must wait for data.** "Only features we actually use" is right and unanswerable today. Ship the telemetry lane first (2.5), read it for four weeks on vaults.sgit.ai, then prune with a reason per commit (P2-D7). Anything sooner is a guess dressed as a decision.

The one genuinely new primitive is **the server reading a vault as a client** (a `Vault__Reader` opening a vault with a read key from inside the API). Everything else is composition of things that exist.
