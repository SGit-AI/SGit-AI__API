SGit API

The server side of the sgit protocol: a service whose whole job is to store ciphertext under opaque ids and give it back. These docs practice what they preach — everything below is being read out of an encrypted vault served by this static host: your browser derived the filenames from a published read-only key, fetched ciphertext with plain GETs from this same origin, and decrypted it locally with the Web Crypto API. There is no server here, which is the point.

The credential, in the open

  
The read key is published deliberately. It grants read, and only read — it is derived
  one-way from the vault key and cannot be turned back into write access. The write key is
  escrowed out-of-band and has never entered the repository.

  
c28b118c9a7a101910efa24a3a49b6cc6dbec8e8dcdc8fea671e89cecb0ab817:ivpijuvg

  
From the CLI (note --read-key — the current CLI release does not parse the
  prefixed shorthand) against a live SG/Send server holding this vault, or — once the CLI
  ships static reads (proposal filed) — against this very page's origin:

  
sgit clone --read-key c28b118c9a7a101910efa24a3a49b6cc6dbec8e8dcdc8fea671e89cecb0ab817 ivpijuvg

Reads are plain GETsThe ciphertext paths are the live API's read paths, served here by GitHub Pages; the repo's CI serves the same tree from a stdlib file server and asserts byte-identity

    
The host cannot read the docsThis origin stores only obj-cas-imm-* ciphertext; the decryption you just benefited from happened in this tab

    
Writes and auth break, by designA published vault is a read-only snapshot; the read key is the whole credential and the ciphertext is the protection

The audit, honestly

  
Before publication the working tree and the git index were scanned: the vault key and
  push token live only in the git-ignored .sg_vault/local/ tier (a unit test
  fails the build if that ever changes); no private-key blocks and no tokens appear in
  tracked files; the vault's own content was written for publication and contains no
  credential other than the deliberately published read key above. The vault has not yet
  been pushed to a production SG/Send server — its named branch was forwarded via a local
  in-memory instance of the same service, so the git repository and this projection are
  currently the authoritative copies.
